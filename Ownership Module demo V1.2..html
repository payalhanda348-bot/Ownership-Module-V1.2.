Ownership Module: governed state

Governed State has four parts: A Ownership, B Agreements and Relationships, C Rights over the Work, and D Version. The Authority Root is read from A and never stored. Make a change at the bottom and see why it is accepted or rejected.

How to read this in 3 steps

  1. Press Load an example in section B. It fills in a rental, a delegation and two IP licences.
  2. Read A to D. A says who owns it, B and C say what has been granted, and D counts the changes.
  3. Press Revoke on any card, or use Make a change. Then watch the lifecycle and the checks update.

                        Authority Root

                        The central authority-evaluation and state-transition mechanism. It reads the governed state (A to D), evaluates authority, applies the lifecycle rules and preconditions, tests the invariants on a proposed state, and only then commits. It stores nothing itself, and nothing changes the state any other way.

                        Authority, read from the governed state

                        Three shapes. None is stored: each is evaluated from A, B, C and D every time it is needed.

                                      Test controls

                                      To see it: grant an exclusive licence, turn on the first bug, then grant a second exclusive licence for the same use. The precondition is skipped, but the draft breaks an invariant and is rolled back. For the second bug, set “Other party must accept first” to No and rent the token twice.

                                      History (append-only)

                                      Every attempt, accepted or rejected, with who was ticked. Only accepted changes raise the version. A reverted on-chain transaction writes nothing, so the contract may need another way to record rejections.

                                        Failure and recovery

                                        Live in this demo When something fails

                                        • A rejected change writes nothing. The owner, shares and agreements stay exactly as they were, and the attempt appears in History.
                                        • If Verification fails or there is a compliance freeze, authority is suspended. Nothing can change until it clears.
                                        • A request built on an old version is rejected and has to be rebuilt on the current one.

                                        Planned, not active When the owner’s key is lost

                                        • The owner names a recovery wallet in advance.
                                        • If the key is lost, the recovery wallet asks to move the claim to a new address, and a delay starts.
                                        • The current owner can cancel during the delay. If nobody cancels, the claim moves when the delay ends.
                                        • Only the claim moves. The shares stay as they are.
                                        • How active agreements are treated on recovery is still to be decided.
